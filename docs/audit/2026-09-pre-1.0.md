> **Status (October 2026, after M32):** every finding in this audit (W1–W18, D1–D30, A1–A10,
> and the chaos baseline) is closed, and each is covered by a passing test on `main`
> (`crates/renox/tests/it/web_security.rs`, `data_resilience.rs`, `background_resilience.rs`,
> `api_foundations.rs`, `extension_points.rs`, and `tests/chaos/run.sh` in CI). The ROADMAP
> M13/M14 checklists have no open item. This file is kept as a historical record; the current
> comparison with Laravel is [2026-10-laravel-parity.md](2026-10-laravel-parity.md).

> **Status since:** this audit is a snapshot of `main` after M12; its findings are kept as
> they were written. All are fixed: W1–W18 and D1–D30 in M13a/M13b (D8, transaction-aware
> dispatch, in M13b as `dispatch_in`), A1–A10 in M14 (A5, trusted proxies, already in M13a
> with W18). Some items the audit put out of scope were built since: cursor pagination
> (M19a), job chains and batches (M20b), the queue dashboard (M20c) and browser tests through
> `TestApp::serve` (M21c). See [ROADMAP.md](../../ROADMAP.md) for each milestone.

Before freezing the API as 1.0, Renox (main after M12, `385319f`) was audited three ways:
1. A feature comparison with Laravel 11/12, checked against the code.
2. 59 probes of negative flows in the web layer.
3. 49 probes of the data and background layers, plus **chaos tests**: faults injected into a
   running app on PostgreSQL 17 and SQLite.

Each finding has a stable ID. The M13 and M14 checklists in [ROADMAP.md](../../ROADMAP.md) refer to
these IDs.

## Where the probes are

The probes are tests that assert the *correct* behaviour, so a failing probe is a finding. They're
committed on two **local** branches of the repository, not on main and not pushed:

| Branch | Files |
|---|---|
| `probe-web` | `crates/renox/tests/it/probe_web.rs` (59 tests) |
| `probe-data` | `crates/renox/tests/it/probe_data.rs` (33), `probe_bg.rs` (17), `examples/probe-chaos/` (the app used for the chaos runs) |

To run them: `git worktree add ../renox-probe-web probe-web`, then in that worktree
`cargo test -p renox --test it probe_`. Add `--features postgres` with `TEST_DATABASE_URL` set for
PostgreSQL. As each M13 item is fixed, its probe moves to main as a regression test and must pass.

Severity: **H** high, **M** medium, **L** low, **I** info.

## C: chaos baseline

| Fault injected into a running app | Behaviour | Status |
|---|---|---|
| PostgreSQL stopped, then started | `/health` answers 503 in 2 s. The pool and workers recover with no restart (first request 0.16 s after start). | good |
| PostgreSQL paused (hangs) | A running request waits 90.8 s; new requests 30 s, then 500. | D4 |
| SQLite held locked by another process | Reads and `/health` stay 200 (WAL). Writes get 500 after the 5 s busy timeout and recover. Jobs are stranded for 15 min. | D6 |
| Storage directory made read-only | A clean 500 that recovers. The log doesn't name the path. | good, D30 |
| SIGTERM while jobs run | Jobs finish within the 30 s grace; a longer one is cut off with a warning and retried after 15 min. | good |
| SIGKILL while jobs run | Retried after 15 min, but without the `MAX_ATTEMPTS` limit. | D2 |
| A panic in a job, task, handler or listener | The worker or task stops for good; the handler drops the connection. | D1, D3, D9 |
| SMTP port closed, or a server that never answers | A closed port fails fast and queued mail retries into `failed_jobs`. A silent server holds direct sends past 8 s. | D22 |

## A: gaps compared with Laravel

About two thirds of Laravel's core features exist, some done Renox's way on purpose:
- no Eloquent relations (no reflection in Rust);
- raw SQL migrations;
- the queue in the app's own database;
- htmx instead of Vite/Livewire.

**Must settle before 1.0.** Changing these later would break apps:

| ID | Gap |
|---|---|
| A1 | `#[non_exhaustive]` or builders for public types that will grow: `Error`, `notifications::Channel`, `Mail`, `Config`, `Environment`, `CspMode`, `RouteInfo`, `FailedJob`, `DatabaseNotification`, `Locale`, `Inspected`. |
| A2 | A policy on public dependencies. `pub use axum` / `sqlx`, `db.sqlite()`, `Routes::route(MethodRouter)` and `cors_layer(CorsLayer)` tie Renox 1.x to pre-1.0 crates. Either hide them or document that Renox's major version follows theirs. |
| A3 | `Error::Status(code, message)` (and an `abort` helper) for 409, 402 and other statuses. |
| A4 | Gates that can use the database (async, or with `AppState`), and a `User` apps can extend: roles, extra registration fields. |
| A5 | Trusted proxies / the real client IP (W18). |
| A6 | Mail: `from`, `cc`, `bcc`, `reply_to`, several recipients, attachments (invoice PDFs). |
| A7 | Custom notification channels (WhatsApp, SMS), and notifying addresses that aren't users. |
| A8 | App extension points: template functions and filters (money, dates), shared view data, typed app state, `App::layer` for global middleware. |
| A9 | App commands (`App::command`), e.g. to create the first admin or run an import. ROADMAP promised them in place of Tinker. |
| A10 | Route groups with a path prefix and a name prefix. |

**Should have (additive, can follow 1.0):**
- transaction-aware dispatch (D8);
- more validation rules (regex, before/after dates, digits, same/different, not_in; `unique`/`exists` with extra conditions; a `Rule` trait; per-item rules for `Vec`);
- query builder: `or_where`, `where_between`, aggregates, bulk update, upsert, `fetch_as::<T>()`;
- weekly, monthly and cron schedules;
- rate limits and login locks stored in the database for several servers;
- auth events, password confirmation, profile pages;
- cache increment and locks;
- a test clock, event fakes, `assert_session_has`;
- an error-reporting hook and JSON logs;
- cache-busting `asset()`, compression and request timeouts;
- more generators (notification, event, command, test, a CRUD scaffold);
- number, currency and date formatting per locale.

**Out of scope on purpose:** Eloquent-style relations, a schema builder, several connections, cursor pagination, job batching/chaining, a Horizon dashboard, websockets, OAuth/2FA (plugin candidates), Vite, Tinker, browser tests.

## Readiness vs Laravel (after M13)

After the M13 hardening, three read-only reviews looked again at what would stop a developer from
choosing Renox over Laravel. They covered the features against Laravel 11/12, test and example
coverage, and developer experience. The plan that follows from them is ROADMAP M14–M17 and v1.0.

**Verdict.** Renox isn't ready to compete with Laravel head to head. It fits one niche well: a solo
developer or a small team shipping an HTML-over-the-wire (htmx) app on one server, deployed as one
binary with SQLite. Reliability and security are ahead of most young frameworks:
- 225 integration tests, about half of them on failure paths;
- the chaos suite in CI;
- the W and D findings fixed with regression tests.

What turns developers away is not bugs but the gaps below.

**Deal breakers, most serious first:**

| # | Kind | Gap | Plan |
|---|---|---|---|
| 1 | Blocker | **Not released.** Only 0.0.1 placeholders are on crates.io. `rnx new` depends on the git main branch without a tag, so `cargo update` pulls an API that is still changing. There is no docs.rs page, semver promise or changelog. | M14a (pin), v1.0 |
| 2 | Blocker | **The data layer.** No relations or eager loading, and no guide for one-to-many or many-to-many without N+1 queries. The query builder has no `select`, joins, `or_where`, aggregates besides `count`, or bulk update. Raw SQL returns untyped rows. | M15 |
| 3 | Blocker | **Trust.** One maintainer, no SECURITY/CONTRIBUTING/CHANGELOG, no guide site, starter kit or package ecosystem. | M16, v1.0 |
| 4 | Major | **Build weight.** A new app compiles about 300 crates. `aws-lc-sys` (a C/CMake build) comes in by default through reqwest, which only analytics uses, and through lettre. `fake` is a runtime dependency. The Dockerfile doesn't cache dependencies. | M16 |
| 5 | Major | **Extension points** (A4, A6–A10): template filters, global middleware, route groups, extending `User`, app commands, mail attachments. | M14 |
| 6 | Major | **Multi-server limits aren't documented.** Rate limits, the login lock and the memory cache are per process. | M16 |
| 7 | Major | **Debugging.** The debug error page is a bare error chain, and a misspelled template variable renders as empty. | M14b |
| 8 | Major | **No cache-busting.** `asset()` doesn't version the app's own files, so visitors can get old CSS/JS for an hour after a deploy. | M16 |

Inherent to Rust, so they can only be reduced:
- compile time on every Rust change;
- no reflection, so no Eloquent-style dynamic relations;
- SQL checked at runtime when it must run on both databases.

**Test gaps:**
- No end-to-end test of `rnx new` and the generators; their output is never compiled.
- The S3 path never runs.
- The SQLite-only build is never compiled, because examples switch on `postgres`/`uuid` for the whole workspace build.
- The macros have no tests.
- A few public APIs are tested only indirectly: session `pull`/`reflash`, `HxRedirect`/`HxRefresh`, `Validator::rule`, schedule constructors and offsets, signed URL tampering.
- No MSRV, cargo-deny, coverage or semver checks in CI.

All of these are in M16.

**Example gaps:**
- There is no full app.
- No example covers relations and joins, transactions, cache, gates, admin search and sort, HTMX recipes (inline edit, infinite scroll, modals), Alpine components, S3, or a deploy directory.
- Examples have no READMEs.

All of these are in M17.

**Where Renox is ahead of stock Laravel:**
- one-binary deploys with views, translations and public files embedded;
- scheduled runs claimed once across servers;
- idempotent webhook ingestion;
- CSP nonces with Alpine's CSP build;
- built-in SEO, sitemap and GA4;
- `db:shell` without a database client;
- `make:deploy`;
- a chaos suite in CI;
- Rust's type safety.

## What held up

- Tampered, foreign-key and oversized session cookies become a guest session.
- Login rotates the CSRF token. A password change logs out other sessions.
- CSRF works on every method and on spoofed ones.
